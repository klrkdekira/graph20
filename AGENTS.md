# SRD 5.2.1 System JSON

## Project purpose

This repository turns the local `SRD_CC_v5.2.1.md` into a modular SRD 5.2.1 reference corpus using JSON-LD 1.1 and JSON Schema Draft 2020-12. `SPECIFICATION.md` is the source of truth for architecture, scope, extraction rules, and acceptance criteria.

## Source discipline

- Treat `SRD_CC_v5.2.1.md` as the authoritative in-scope source. It is CC-BY-4.0: the attribution statement must survive in the source record, manifest, README, and llms-full output.
- Do not add material from rulebooks, wikis, or other SRD versions without a separate source record and rights metadata.
- Preserve source wording in `rulesText`/`description`; structured fields are indexes, not replacements.
- Never silently repair OCR/conversion anomalies in parser code. Every normalization goes through `objects/sources/extraction-overrides.json` with observed tokens, proposed fix, rationale, and status.
- Never invent missing values (e.g. truncated ability-table cells stay omitted).

## Data conventions

- JSON-LD 1.1; JSON Schema Draft 2020-12; base IRI `https://cheeleong.dev/graph20/`.
- Use `@id` node references for semantic links; `$ref` only for schema composition. Predicates declared `@type: "@id"` must never be emitted as bare strings.
- Properties camelCase; slugs and filenames lowercase kebab-case; classes PascalCase.
- Everything under `objects/` (except `extraction-overrides.json`) is generated by `scripts/`; never hand-edit generated files.

## Change workflow

1. Change scripts/schemas, then rebuild: `make extract manifest bundle llms-full search-index`.
2. Verify with `make test validate schema`, and `make determinism` before finishing (`make check` runs everything).
3. Keep generated output deterministic: no timestamps, no randomness, sorted listings.
4. Do not implement a rules engine, character builder, or campaign state in this corpus.
